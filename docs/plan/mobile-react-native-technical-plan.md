# React Native 移动端技术方案 v1

## 1. 文档定位

- 本文档用于承载 `Android + iOS` React Native 移动端的新产品线方案。
- 目标是在当前仓库基础上建设一套与桌面端能力高度对齐、可持续演进、可维护、可验证的移动 IM 客户端。
- 本文档重点记录：
  - 架构选择
  - 复用边界
  - 技术栈建议
  - 分层设计
  - 同步开发策略
  - 里程碑与验收原则
  - 风险与规避方案
- 主计划中的总体目标、关键节点和状态统一维护在根目录 `task_plan.md`。

## 2. 当前现状与结论

### 2.1 仓库现状

- `apps/mobile` 已重建为真正的 `React Native` 原生双端工程，仓库内已存在：
  - `android/`
  - `ios/`
  - `index.js`
  - `metro.config.js`
  - `babel.config.js`
  - React Native 应用入口与基础测试
- `packages/shared` 已经沉淀出较可复用的协议层资产：
  - API transport
  - 服务端返回类型
  - WebSocket 消息类型
  - 消息 / 会话 / 通话相关领域类型
  - 一部分平台无关工具函数
- `packages/app-core` 已新增，承载移动端共享应用层、鉴权、同步、本地仓储接口与 controller。
- 旧 `packages/ui` 与 `packages/native-bridge` 因为空壳且无有效抽象价值，已从仓库移除。
- 服务端当前已经具备或接近具备以下移动端前置条件：
  - 登录设备注册 `device_type` / `device_name` / `push_token`
  - 会话、消息、同步、已读、治理、搜索等协议面
  - 实时通话 `call.*` 信令
  - 群通话 `LiveKit` 房间配置下发
  - `voice_message` / `call_record` 消息类型

### 2.2 结论

- 当前仓库已经完成从旧移动壳到 `React Native` 原生双端方案的切换。
- 后续移动端演进应建立在现有 React Native 宿主和 `app-core` 共享层上，而不是回到 Web 容器思路。
- 复用重点应放在“协议、领域逻辑、状态机、同步策略、数据映射”，而不是强行复用 Web / Electron 组件。
- Android 和 iOS 应同步开发，共用一套产品 backlog、领域层和大部分页面逻辑，只把能力差异收敛在平台适配层。

## 3. 产品目标与范围

### 3.1 目标

- 功能上与桌面端几乎一致，覆盖：
  - 登录 / 注册
  - 联系人与群
  - 会话列表
  - 单聊 / 群聊
  - 文本 / 图片 / 文件 / 语音消息
  - 搜索、收藏、置顶、撤回、回复、转发
  - 群治理、联系人治理
  - 用户资料与设备摘要
  - 实时音视频通话
  - 通知与多设备状态协同
- 体验上符合主流移动 IM 习惯，参考 `WhatsApp`、`Telegram` 一类产品的交互密度、导航方式和手势体验，但不做像素级照搬。
- 工程上保证：
  - 高复用
  - 易测试
  - 易拆分
  - 易扩展
  - 平台差异可控

### 3.2 首版明确不做

- 与桌面端完全不同的独占产品形态
- 大量仅为“统一视觉”而牺牲移动端原生体验的跨端 UI 复用
- 一开始就引入复杂会议能力：
  - 屏幕共享
  - 直播 / 旁听
  - 主持人控场
  - 美颜 / AI 降噪
  - 通话录制
- 未经过 POC 就把所有能力绑死在单一第三方 UI 框架上

## 4. 冻结的核心技术决策

### 4.1 客户端架构

- 客户端采用 `React Native + TypeScript`。
- 使用 `React Native New Architecture + Hermes`。
- 仓库已移除 `Capacitor` 与 `Ionic` 遗留依赖和配置。
- Android / iOS 维持单仓同构开发。

### 4.2 工程路线

- `apps/mobile` 重建为真正的 React Native 应用。
- 推荐优先采用 React Native CLI 路线，而不是 Expo Managed。
- 原因：
  - 后续需要深度接入：
    - 推送
    - VoIP/来电能力
    - 音视频通话
    - 本地数据库
    - 后台唤醒
    - 权限与设备能力桥接
  - 这些能力对原生模块控制权要求较高。
  - 若后续使用 Expo，也应是 `prebuild/dev client` 思路，而不是把首版建立在受限托管模式上。

### 4.3 复用原则

- 直接复用：
  - `packages/shared` 中的平台无关类型、协议、工具函数、状态机
  - 服务端现有 API / WebSocket / call 协议
- 抽取后复用：
  - 启动同步编排
  - 会话 / 消息 mapper
  - 搜索、收藏、置顶、撤回等消息域规则
  - 通话状态派生规则
- 不直接复用：
  - Web / Electron React 组件
  - 面向 DOM 的交互逻辑
  - Electron 本地桥接与数据库实现

### 4.4 UI 策略

- 移动端界面按 React Native 原生交互重建。
- 不做“桌面 UI 强行缩放到手机上”。
- 设计风格要求：
  - 信息密度接近主流 IM
  - 导航明确
  - 动效克制
  - 长列表流畅
  - 常用操作靠近拇指热区
- 建议采用：
  - 底部主导航
  - 会话优先入口
  - 长按操作菜单
  - 左滑快捷动作
  - 聊天输入区贴近原生手感

## 5. 推荐技术栈

### 5.1 基础运行时

- `react-native`
- `typescript`
- `hermes`

### 5.2 路由与页面组织

- `@react-navigation/native`
- `@react-navigation/native-stack`
- `@react-navigation/bottom-tabs`
- `react-native-screens`
- `react-native-safe-area-context`

说明：

- 采用标准移动导航栈，便于会话列表、聊天页、资料页、搜索页、通话页的层次拆分。

### 5.3 状态管理

- 服务端状态：`@tanstack/react-query`
- 客户端交互状态：`zustand`
- 原则：
  - 服务端状态与 UI 瞬态状态分离
  - 会话、消息、联系人、资料等远端资源统一进入 query / repository
  - 输入框、弹层、草稿、手势态等留在本地 store

### 5.4 本地持久化

- 轻量 KV：
  - `react-native-mmkv`
- 结构化本地数据：
  - `SQLite`
  - 优先选择 JSI 驱动方案，在 `M1` 通过 POC 固化具体包

说明：

- `MMKV` 适合：
  - token
  - 当前账号上下文
  - feature flag
  - 轻量偏好配置
- `SQLite` 适合：
  - 会话快照
  - 消息列表
  - 同步游标
  - 缺口修复状态
  - 附件索引
- 不建议把消息主存储放在纯 KV 或纯内存 store。

### 5.5 列表、动效与手势

- `@shopify/flash-list`
- `react-native-reanimated`
- `react-native-gesture-handler`

说明：

- 聊天列表、会话列表、搜索结果、附件中心都属于高频长列表，优先解决滚动性能和手势冲突。

### 5.6 媒体与文件能力

- 图片 / 视频选择：优先 `react-native-image-picker`
- 按住录制短视频：`react-native-vision-camera`（内联相机预览 + `Recorder` 录制，长按后弹出预览页右上角发送）
- 文件选择：优先 `react-native-document-picker`
- 权限管理：`react-native-permissions`
- 图片预览与缓存：根据首版性能情况补充专用图片组件

### 5.7 语音消息与实时通话

- 语音消息：
  - 录音、播放、波形能力采用成熟原生模块
  - 首版以稳定为先，不追求复杂音频编辑
- 单聊实时通话：
  - 复用现有 `call.*` 信令
  - 媒体层使用 `react-native-webrtc`
- 群聊实时通话：
  - 复用现有群通话状态机
  - 媒体层使用 `@livekit/react-native`

说明：

- 直接把单聊和群聊统一到同一媒体 SDK 看似简单，但会引入服务端和现有桌面实现的额外改造成本。
- 当前更合理的策略是：
  - 先复用现有协议与服务端能力
  - 在移动端分别适配单聊 `WebRTC P2P` 与群聊 `LiveKit`
  - 再评估未来是否收敛媒体实现

### 5.8 通知与来电能力

- 普通推送：
  - Android：`FCM`
  - iOS：`APNs`
- React Native 侧建议：
  - 消息推送：`@react-native-firebase/messaging`
  - 本地通知：`notifee`
  - 来电系统集成：`react-native-callkeep`

说明：

- 冷启动消息提醒与来电提醒不能只依赖应用前台 WebSocket。
- 推送与来电系统集成属于移动端成熟 IM 的必要能力，应单独作为后续里程碑收口。

### 5.9 质量与验证

- 单元测试：
  - 共享包与领域逻辑继续用 `node --test`
- 移动组件 / hooks：
  - `@testing-library/react-native`
- E2E：
  - `Detox`

说明：

- 首版不追求所有场景都做全量 E2E，但至少要覆盖：
  - 登录
  - 会话列表
  - 基础发送接收
  - 推前台同步恢复

## 6. 分层设计

### 6.1 推荐目录方向

- `apps/mobile`
  - React Native 应用壳
  - 页面、导航、平台适配、原生模块接入
- `packages/shared`
  - 现有协议类型、基础工具继续保留
- `packages/app-core`
  - 新增，承载平台无关的应用领域逻辑
- `packages/mobile-ui`
  - 新增，可选，用于沉淀移动端设计 token、基础组件、样式约束
- 原生桥代码
  - 首先收敛在 `apps/mobile` 内部
  - 只有在 Android / iOS 之间出现稳定共享接口时，再考虑单独抽包

### 6.2 `packages/app-core` 目标

- 目标不是放 UI，而是放跨端应用逻辑：
  - 会话与消息仓储接口
  - 同步 orchestrator
  - websocket 事件归并
  - 通话状态派生
  - 草稿、置顶、收藏、搜索等领域服务
  - 统一 mapper / selector

说明：

- 当前很多逻辑散落在 Web / Electron 端实现里。
- 移动端启动前应先把可复用的“应用域逻辑”抽上来，否则会变成第三套实现。

### 6.3 平台边界

- `app-core` 只依赖接口，不依赖 React Native 或 DOM。
- `apps/mobile` 负责：
  - 页面
  - 导航
  - 本地数据库驱动接线
  - 推送、权限、系统分享、来电系统等平台能力
- Electron / Web 后续也可逐步回收复用 `app-core`。

## 7. 同步开发策略

### 7.1 Android / iOS 并行规则

- 只有一套功能 backlog。
- 每个里程碑同时定义：
  - 共享层完成条件
  - Android 完成条件
  - iOS 完成条件
- 不接受只在一个平台完成大量主流程后再“移植”到另一端。

### 7.2 平台差异处理方式

- 先定义公共 contract，再做平台 shim。
- 允许差异的地方：
  - 权限弹窗
  - 推送配置
  - 来电系统集成
  - 文件系统与媒体采集细节
- 不允许差异漂移的地方：
  - 业务协议
  - 同步规则
  - 消息状态语义
  - 通话状态机
  - 核心页面信息架构

### 7.3 开发节奏

- 每个里程碑先做共享层与基础页面骨架。
- 再补 Android / iOS 平台能力差异。
- 最后统一做双端 smoke 回归。

## 9. 关键验收标准

### 9.1 工程

- Android 与 iOS 都可以稳定本地运行。
- workspace 内 lint / type-check / test 可执行。
- 共享领域逻辑不会复制出第二套、第三套实现。

### 9.2 产品

- 高优先级 IM 主路径与桌面端保持一致：
  - 登录
  - 会话
  - 消息
  - 联系人
  - 群
  - 搜索
  - 资料
- UI 具备移动端原生感，不是桌面网页缩略版。

### 9.3 性能

- 会话列表、聊天列表滚动稳定。
- 长列表与媒体消息不会出现明显卡顿。
- 冷启动与前后台恢复可接受。

### 9.4 可靠性

- 断网 / 重连 / 前后台切换后状态能正确恢复。
- 本地同步游标、消息缺口与已读语义与现有桌面规则保持一致。
- 通话状态不能因多设备或前后台切换出现分叉。

## 10. 主要风险与规避

### 风险 1：继续把移动端当作 Web 容器扩展

- 影响：
  - 通知、通话、权限、后台能力都会受限
- 规避：
  - 尽快冻结 React Native 原生路线

### 风险 2：复用策略错误

- 影响：
  - UI 不适配
  - 业务逻辑重复实现
- 规避：
  - 复用领域逻辑，不强复用 DOM 组件

### 风险 3：本地数据层过轻

- 影响：
  - 历史消息、重连、离线恢复体验不稳定
- 规避：
  - 从首版开始建设 SQLite 消息仓储与同步状态持久化

### 风险 4：推送与来电系统后置过晚

- 影响：
  - 真机体验与桌面端差距过大
- 规避：
  - 在规划上单列 `M7`，不要把其视为“上线后再说”

### 风险 5：Android / iOS 分叉

- 影响：
  - 后续维护成本快速上升
- 规避：
  - 一套 backlog
  - 一套领域层
  - 一套验收标准
  - 平台差异只放在 adapter 层

## 11. 当前建议执行顺序

1. `M0`、`M1`、`M2`、`M3`、`M4`、`M5`、`M6` 已完成，当前进入 `M7`。
2. 在 `M7` 先把通知、后台能力、真机构建验证与发布收口做稳，再进入首发准备。
3. `M7` 必须在首发前完成最小推送与后台能力收口。

## 12. 当前结论

- 当前移动端工作已经完成产品线切换，后续不再回到旧移动壳思路。
- 最关键的架构策略是：
  - 业务逻辑上移复用
  - UI 按移动端原生范式重建
  - Android / iOS 同步推进
  - 推送、通话、同步、本地数据从一开始就按真实移动端产品设计
- 当前已完成 `M6`，语音消息、前台通话信令与通话状态收敛已建立在 `@mushroom/app-core`、移动端实时层和 React Native 宿主之上。
- 后续编码应从 `M7` 开始，继续沿用 `@mushroom/app-core` 与原生 React Native 页面拆分路线推进。
